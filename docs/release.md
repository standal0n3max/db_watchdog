# Публичная выгрузка датасета

Документ описывает команду `release`: что попадает в публичный слой, как
устроены стабильные идентификаторы, что гарантирует манифест и как проверить
готовый релиз. Причина появления — требование трека Datasets and Benchmarks к
доступности данных: «Datasets should be easily accessible … without requiring
personal requests».

## Границы: что выкладывается, а что нет

| Слой | Попадает в релиз | Поле |
|---|---|---|
| Публичная задача | да | `id`, `core`, `source`, `license`, `head`, `base`, `oracle`, `split`, `area`, `goal`, `contract`, `graded_by` |
| Приватный oracle | только `--with-oracle` | `reverse_patch`, `test`, `reference`, `test_files`, `expected_tests`, `oracle_command` |
| Индекс графа | нет | — |
| Клон ядра | нет | — |
| Прогоны и трассы | нет | — |

Разделение то же, что у `validate_public`: публичный слой не содержит ни одного
фрагмента diff и никогда не несёт ответ задачи. Собирать релиз со
`--with-oracle` и публиковать его вместе с `tasks/` нельзя: `reverse_patch` и
`reference` раскрывают эталон.

## Стабильные идентификаторы

`id` = `<ядро>__<head[:12]>`, где `head` — полный sha коммита-эталона. Полный
`head` лежит в записи целиком, поэтому короткий `id` однозначно разрешается в
задачу. Идентификатор выведен из содержимого коммита, а не из номера строки или
порядка обхода, поэтому не меняется при повторной сборке. Совпадение коротких
префиксов — ошибка сборки, а не молчаливая перезапись.

## Состав релиза

```
tasks/<id>.json     300 публичных задач
oracle/<id>.json    приватный слой (только с --with-oracle)
split.json          dev/tune/holdout и holdout_sha256
licenses.md         лицензии источников из repos.toml
README.md           инструкция внутри самого релиза
manifest.json       счётчики, лицензия, sha256 каждого файла, content_sha256
```

`split.json` несёт разбиение `dev`/`tune`/`holdout`. Список `holdout` совпадает
с замороженным `constraints/benchmark-holdout.txt`, и `holdout_sha256` в
манифесте равен хэшу `split_module.holdout_sha256` для текущего замороженного
набора. Это связывает релиз с тем же holdout, по которому считается парная
оценка.

## Детерминизм манифеста

В манифест не попадают ни время сборки, ни пути хоста, поэтому он
байт-детерминирован: два ребилда подряд дают одинаковый `content_sha256`.
Расхождение означает изменение данных, а не момента запуска. Сводный хэш
считается по списку `«путь sha256»` для всех файлов, кроме самого манифеста, в
алфавитном порядке; JSON пишется с сортировкой ключей и фиксированным отступом.

## Проверка

```bash
uv run python -m db_pipeline.benchmark release-verify --target data/releases/0.1.0
```

Команда возвращает `ok: true` только если сходятся все условия:

- каждый файл из манифеста присутствует и его `sha256` совпадает;
- сводный `content_sha256` совпадает с пересчитанным;
- лишних файлов, которых нет в манифесте, не появилось;
- ни в одной публичной задаче нет фрагментов `diff --git`, `+++ b/` или `@@`.

Ненулевой код возврата — релиз повреждён или подменён. Это позволяет проверять
выгрузку независимо от того, где она распакована.

## Пересборка

```bash
uv run python -m db_pipeline.benchmark release --version 0.1.0
uv run python -m db_pipeline.benchmark release --version 0.1.0 --force   # перезапись
uv run python -m db_pipeline.benchmark release --version 0.1.0 --with-oracle
```

По умолчанию каталог `data/releases/<версия>`. Непустой каталог не
перезаписывается без `--force`, чтобы случайный запуск не стёр выгрузку.
